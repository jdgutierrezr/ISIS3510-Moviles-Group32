# BQ11 — Neighborhood quest activity

BQ11 asks which neighborhoods have the most quest activity for local business partnerships. Activity means **completed quest participations in the rolling last 30 days**, across all users. One completion record counts once; `active_participants` and `active_places` are distinct counts. Pending, abandoned, undated and future completions are excluded. The lower and upper window boundaries are inclusive.

## Deployment

Run `sql/bq11.sql` in the existing project's Supabase SQL Editor **after** `schema_creation.sql`, `rls_rules.sql` and `rpc_functions.sql`. Do not run the clean/reset script on a live project. This additive migration can be rerun and does not modify the signatures of `nearby_quests` or `nearby_places` used by Android and iOS.

The migration adds the `neighborhoods` catalog, a nullable `places.neighborhood_id` foreign key, indexes and `neighborhood_quest_activity(p_days integer default 30)`. It does not infer neighborhoods from place names, addresses or coordinates. An administrator must populate the catalog with verified neighborhood names, cities and representative coordinates, then assign existing places to their verified neighborhood IDs. Representative coordinates locate activity markers; they are not neighborhood boundaries.

The existing seed catalog has no verified neighborhood membership. It remains unassigned until mapped. For a complete demonstration with synthetic data, use the optional visualization seed below. Use these audits after adding verified catalog rows and setting `places.neighborhood_id`:

```sql
select p.id, p.name, p.address, p.latitude, p.longitude
from public.places p
where p.neighborhood_id is null
order by p.name;

select n.id, n.name, n.city, count(p.id) as mapped_places
from public.neighborhoods n
left join public.places p on p.neighborhood_id = n.id
group by n.id
order by n.city, n.name;
```

Do not run `tests/bq11_fixtures.sql` on a hosted project: its neighborhoods and users are synthetic test data. Deployment is complete only after both applying the migration and populating verified neighborhood mappings.

## Optional visualization seed

For the seeded demo project, apply `sql/bq11.sql` and then **`sql/bq11_seed_data.sql`**. The seed is a separate opt-in step. It does not require resetting or rerunning the original `seed_data.sql`.

On first application, the 30-day BQ11 report includes:

| Neighborhood | Completed quests | Participants | Active places |
| --- | ---: | ---: | ---: |
| Demo · Barrio Norte | 8 | 4 | 2 |
| Demo · Barrio Centro | 4 | 3 | 2 |
| Demo · Barrio Sur | 2 | 2 | 1 |
| Demo · Barrio Oeste | 0 | 0 | 0 |

In iOS, open **Map → Neighborhoods**. The answer for the demo dataset is **Barrio Norte has the most activity and is the first partnership priority**, followed by Centro and Sur. Oeste demonstrates the zero-activity state. Six demo quests have coordinates within 5 km of the default Bogotá center, so Map → Nearby also shows their pins and distances.

These labeled demo neighborhoods are synthetic, not verified boundaries or real partnership evidence. Existing unmapped places remain unmapped, and their completions remain visible in the coverage warning. Other mapped data may change the global ranking.

The seed creates four analytics-only identities without sign-in credentials. Only these identities receive the 14 seeded completions and checked objective records. Existing accounts, their quest history, pending quests, progress, XP, streaks, reviews, review photos and existing place ratings are not updated. The original test accounts can still start/finish/review the new demo quests themselves, which legitimately adds activity to BQ11.

Reruns insert only missing rows. They do not duplicate completions, rejuvenate their dates, reset user progress, overwrite submitted reviews or award XP. Seeded activity ages out of the rolling window naturally; starting and completing quests through the app adds fresh activity. The `e100`–`e140` UUID prefixes are reserved for this demo, with identity/catalog collision checks that abort the seed transaction.

The SQL runner additionally verifies the seed twice, snapshots original quest/profile/review/photo rows, completes a pre-existing photo objective and submits its review, starts/completes/reviews a demo quest, starts another original quest, then reruns the seed and checks that all resulting progress/reviews/rewards and BQ11 activity are preserved.

## API

Authenticated clients call `POST /rest/v1/rpc/neighborhood_quest_activity` with `{"p_days":30}`. The supported window is 1–365 days. The response is a JSON object, not a single-element array:

```json
{
  "window_start": "2026-09-01T00:00:00.000000Z",
  "window_end": "2026-10-01T00:00:00.000000Z",
  "unassigned_completions": 1,
  "neighborhoods": [
    {
      "id": "40000000-0000-0000-0000-000000000001",
      "name": "Test North",
      "city": "Bogotá",
      "latitude": 4.61,
      "longitude": -74.08,
      "completed_quests": 3,
      "active_participants": 2,
      "active_places": 2
    }
  ]
}
```

Rows are ordered by completed quests descending, then name and UUID. Ties mean equal priority; zero-activity neighborhoods are included. Without catalog rows, `neighborhoods` is `[]`; the unassigned count still reports otherwise qualifying completions. Clients must show this coverage gap rather than claiming a complete ranking.

Existing Map calls remain `nearby_quests(p_lat,p_lng,p_radius_km)` and `nearby_places(p_lat,p_lng,p_radius_km)`. Join on `quest.place_id == place.id` for coordinates; distances come from the server in kilometers and are closest first.

## Permissions

Authenticated clients can read neighborhoods but cannot write them. The activity RPC uses `SECURITY DEFINER` with a fixed search path and fully qualified application tables so that aggregation can include users outside the caller's friendship graph. It returns only neighborhood counts, never completion records or user identities. Existing completion RLS remains unchanged. Anonymous access and missing caller identities are rejected. See [PostgreSQL's function security guidance](https://www.postgresql.org/docs/current/sql-createfunction.html#SQL-CREATEFUNCTION-SECURITY).

## Tests

Run isolated SQL integration tests with Docker:

```bash
bash sql/tests/run_bq11.sh
```

This starts a disposable PostgreSQL 17 container, installs the original schema/RLS/RPCs, applies BQ11 twice around fixture insertion, and asserts cross-user counts, time boundaries, invalid windows, permissions, coverage, deletion behavior, empty results and existing nearby contracts. The container is removed on exit.

For iOS SDK integration tests, start the local PostgreSQL + PostgREST server:

```bash
python3 sql/tests/serve_bq11.py --env-file /tmp/wandr-bq11-local-env.json
```

The server binds only to loopback ports 55433/55434 and produces a JWT for its disposable database. It uses the real RPCs, not canned HTTP responses. Stop with Ctrl-C to remove its containers. Fixtures identify Test North (3 completions, 2 participants, 2 places) as the top neighborhood, Test South (1), Test Zero (0), and one unassigned completion.

To run the iOS integration suites from the Swift checkout while that server is running:

```bash
xcodebuild -project Wandr-Swift-group-32.xcodeproj -scheme Wandr-Swift-group-32 \
  -destination 'platform=iOS Simulator,id=YOUR_SIMULATOR_UUID' \
  -derivedDataPath artifacts/build build-for-testing

python3 - <<'PYTHON'
import json, plistlib
from pathlib import Path
products = Path('artifacts/build/Build/Products')
original = next(p for p in products.glob('*.xctestrun') if p.name != 'BQ11-local.xctestrun')
```

Replace the simulator UUID using `xcrun simctl list devices available`. The generated environment file contains only a local test JWT. The optional local helper in the Swift workspace automates these steps; it is ignored by Git.
